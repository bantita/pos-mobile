## Design decisions (fixed — do not re-decide)

- D1 Member TYPE is orthogonal to LEVEL. `level`, `MOCK_LEVEL_CONFIGS`, `levelConfigs`, auto-upgrade stay untouched. Promotion already has an unrelated field `memberType?: 'all'|'new'|'existing'` — do NOT reuse it; the new field is `applicableMemberTypeIds?: string[]`.
- D2 Colors are stored as a token KEY, not hex: `MemberTypeColorKey = 'gray'|'blue'|'green'|'orange'|'red'|'purple'`, mapped in a new constants file to WebColors (web) and Colors (mobile) pairs (fg/bg). Satisfies "no hardcoded colors" on both platforms.
- D3 Store topology: `memberTypeStore` (new) imports `memberStore` lazily inside functions (counts, reassign, rename propagation); `memberStore` imports `memberTypeStore` functions only inside actions (default type in addMember, earn rule in earnPoints). This cycle is safe because no top-level code dereferences the other module (same pattern as categoryStore→productStore). Document this in a comment at the top of both files.
- D4 Type discount — POS mobile `PaymentScreen` (uses the engine via `runCartPromotions`): the adapter synthesizes one extra PromotionConfig when the selected member's resolved type has `discountPercent > 0`: id `member-type:<typeId>`, name `ส่วนลด<ชื่อประเภท> <x>%` (e.g. "ส่วนลดพนักงาน 10%"), benefit `percent_discount{percent}`, condition `member{memberTypeIds:[typeId]}`, `stackMode: STACK_ALLOWED`, `priority: 9999`. Stacking rationale (resolver sorts priority ascending; first NO_STACK wins only if nothing applied yet): priority 9999 is evaluated LAST, so it never blocks an existing promotion; if a NO_STACK promotion was applied it is rejected ("Cannot stack with NO_STACK promotion"), otherwise it stacks with STACK_ALLOWED promos. It therefore appears in `appliedBenefits` (the applied-promotions list) with the Thai name. The adapter stays pure: caller passes the resolved type as a new arg `memberType?: MemberTypeBenefit | null`.
- D5 Type discount — web `WebPOSScreen` does NOT use the engine (manual `billDiscAmt`/`couponDiscount`/`pointDiscount` pipeline). There it is a clearly labelled bill discount line "ส่วนลด<ชื่อประเภท> x%" computed by the shared pure helper `computeMemberTypeDiscount(afterDisc, type)` on `afterDisc` (after manual bill discount, before coupon/points): `grandTotal = max(0, afterDisc - memberTypeDiscount - couponDiscount - pointDiscount)`, coupon still computed on `afterDisc` as today; included in `discountTotal` of the saved sale. Documented as the fallback path in the verification doc.
- D6 Points: one pure helper `calcEarnedPoints(amount, earnRate, type?)` = `type?.earnPoints === false ? 0 : Math.floor(amount / (earnRate||1) * (type?.pointMultiplier ?? 1))`. With default type (earn=true, ×1) result equals today's `Math.floor(amount/earnRate)` → no behavior change. `memberStore.earnPoints` uses it (still adds `totalSpent`, so level upgrades keep working); when points = 0 it updates totalSpent but does not push a 0-point transaction; return type becomes `PointTransaction | null` (all callers ignore the return value — PaymentScreen:211, WebPOSScreen:2713). Displayed "pointsEarned" values in PaymentScreen (~205) and WebPOSScreen (~2685, 2687, 2738) use the same helper.
- D7 Resolution: `resolveMemberType(member)` → the member's type if it exists AND is active, else the current default type. Used for benefits at POS. Badges show the member's own type name (stored or looked-up); inactive type shows "(ปิดใช้งาน)" suffix in back-office only.
- D8 Migration: `memberStore` persist gets `version: 1` + `migrate(persisted, fromVersion)`: when `fromVersion < 1`, every member lacking `memberTypeId` gets `memberTypeId: 'mt-general'`, `memberTypeName: 'ลูกค้าทั่วไป'` (the seeded default id constant `DEFAULT_MEMBER_TYPE_ID`). Export the pure function `migrateMembersToV1(state)` for tests. Any dangling id at runtime is covered by D7. `memberTypeStore` (`name: 'pos-member-types'`, `version: 1`) uses `merge` with exported pure `ensureMemberTypeInvariants(types)`: empty list → reseed; zero or multiple defaults → first active default kept / first active type made default. Member types are configuration, so they are seeded even when `isFreshStore()` is true.
- D9 Management UI location: a new CRM menu item "ประเภทสมาชิก" (key `member-types`, icon `pricetags-outline`) directly after "ระดับสมาชิก" in `WebCRMScreen` MENUS, rendering a new `WebMemberTypeScreen` component (own file, keeps the 1632-line WebCRMScreen from growing). Gated by new permission key `crm_member_types` (label "ประเภทสมาชิก", group CRM; in manager defaults; admin/owner get it automatically): menu item hidden when `!canAccess(user.role, 'crm_member_types')` (user from `useAuthStore`).
- D10 Promotions targeting: engine member condition gains `memberTypeIds`; `CalculationRequest`/`EvaluationContext` gain `memberTypeId`. Adapter adds `memberTypeIds` to the member condition of ANY mapped promo whose `applicableMemberTypeIds` is non-empty (merge into existing member condition for `member_price`, otherwise push a new one). UI: `MemberPriceScreen` (the only mobile form that really persists via `createPromotion`) gets a type multi-select; validation becomes "เลือกระดับสมาชิกหรือประเภทสมาชิกอย่างน้อย 1 รายการ". WebCRMScreen coupon form (`cpLevel`, ~line 628/656) gets an optional type picker → `applicableMemberTypeIds`. `PromoConditionTabs` "สมาชิก" tab gets type chips via optional controlled props (`selectedMemberTypeIds?`, `onMemberTypeIdsChange?`, same pattern as `selectedCouponCampaigns`), with state held in `StorePromoCreateScreen` (its save is mock today — note it, don't wire a new save). `promoStore.validateCoupon` gets optional 4th arg `memberTypeId?` and rejects with "คูปองนี้ใช้ได้เฉพาะประเภทสมาชิกที่กำหนด" when `applicableMemberTypeIds` is set and doesn't match; WebPOS/PaymentScreen pass it. WebPOS member-modal promo eligibility (~2865) also checks types.
- D11 Optional items: `requireStaffLink` — DEFERRED (staffStore holds service technicians; employeeStore linkage would need cross-store identity matching; not low-risk). Broadcast/segment targeting by type — DEFERRED (current `'level'` target in communicationStore is a placeholder count `Math.min(contacts, 200)` with no member↔contact linkage; adding a type target would be equally fake). Reports — IN (low-risk): snapshot `memberTypeId`/`memberTypeName` (+ `memberId`) on new SaleRecords and add a "ยอดขายตามประเภทสมาชิก" card to the CRM ReportsPanel.
