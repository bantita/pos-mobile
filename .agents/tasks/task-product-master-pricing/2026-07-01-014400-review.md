# Per-branch pricing wired into POS, per-line VAT, real CSV import/export

Branch ids are unified to `b1/b2/b3` across `pricingStore` and `mockBranches`, and both POS screens now resolve each cart line's price through a shared pure helper (`resolveCartPrice`) keyed by product CODE and scaled by the chosen UOM ratio, with `POSSaleScreen` switched from static `MOCK_PRODUCTS` to `useProductStore`. `cartStore` replaces its flat 7% VAT with a per-line computation that honours each product's `vatIncluded`/`vatRate` and spreads the bill-level discount proportionally, so inclusive lines never double-add VAT and exclusive lines are now (correctly) added into the grand total. On the product-master side, CSV import/export and the image picker are real (web `<input>`/`FileReader`/`Blob`), price edits log a real audit entry, and the dead `WebPricingScreen` is deleted. All new code is Thai-faced, uses design tokens, and introduces no `any`.

Watch for: (1) **confirmed** — `getGrandTotal` now adds exclusive VAT on top of the discounted subtotal; this is a deliberate, documented change from the prior behaviour (exclusive VAT was silently dropped) and every downstream consumer of `getVatAmount`/`getGrandTotal` must not re-add VAT. (2) **confirmed** — mobile `AddEditProductScreen` edits (image, price) still do not persist to `productStore` because `ProductNavigator.onSaved` only calls `goBack()`; the audit entry fires regardless. Flagged by the author, deliberately out of scope. (3) **confirmed** — branch-price recompute at runtime depends on `useBranchGuard` reading `branchStore`, which is empty at runtime and falls back to `b1`; only verifiable in a browser.

**Verdict**: APPROVED

## High-level view

The pricing wiring is the core of the change. A single pure helper resolves price at the add-to-cart boundary in both POS screens, which keeps the resolution rule (branch doc > central doc > UOM fallback, then × ratio) in one place and makes it unit-testable without React. `POSSaleScreen` now derives its product grid reactively from `productStore` and the active branch, matching the pattern `WebPOSScreen` already used.

The VAT rework changes a real correctness bug: the old flat 7%-on-discounted-subtotal ignored per-product flags and dropped exclusive VAT from the payable entirely. The new code computes each line's VAT from its own flags and keeps inclusive VAT embedded while adding exclusive VAT to the grand total. The grand-total semantics shift is intentional and documented; the risk is any downstream code that assumed VAT was purely informational.

The product-master fixes are self-contained web/mock features with no new dependencies: hand-rolled CSV parse/serialize with BOM handling, flexible Thai header mapping, per-row validation with a real error summary, data-URI image preview, and a `logAction` audit entry gated on an actual price change. The one carried-over gap — mobile edits not persisting — is correctly left untouched rather than silently rewired.

### Price resolution via a single pure helper

`resolveCartPrice(master, uom, branchId)` lives in `src/utils/priceResolver.ts` with no React imports. It calls `usePricingStore.getState().resolvePrice(master.code, branchId)` — keyed by CODE (`P001`), not master id (`p1`), which is the store's actual contract. On a hit it returns `round2(resolved.price * uom.ratio)` with `source` = the doc's `sourceType` (`'branch'`/`'central'`); on a miss it returns `uom.salePrice` with `source: 'base'`. The `source` union (`PricingScope | 'base'`) is type-safe against `ResolvedPrice.sourceType`.

Both POS screens route the cart-line price through it at the `toCartProduct` boundary and pass `activeBranchId` from `useBranchGuard()`. `POSSaleScreen` now builds its product list reactively:

```tsx
const allCartProducts = useMemo<Product[]>(
  () => products.flatMap((m) => m.uoms.map((uom) => toCartProduct(m, uom, activeBranchId))),
  [products, activeBranchId],
);
```

with `products` from `useProductStore` and barcode/long-press/service paths all re-pointed from `MOCK_PRODUCTS` to the live `products` list. The `useMemo` dep arrays include `activeBranchId`, so a branch switch recomputes prices — subject to the runtime caveat that `branchStore` is empty and `useBranchGuard` falls back to `b1`.

One intentional asymmetry worth noting: on a pricing-doc hit the base price is scaled by `uom.ratio`, but on a miss the fallback is `uom.salePrice` directly (the pack's own sale price, not base × ratio). The priceResolver test locks this in (`PACK_UOM` miss → 55, not scaled). This matches Decision C.

### Per-line VAT and the grand-total shift

`computeLineVats(items, ratio)` returns `{ vat, exclusive }` per line. `lineNet = item.subtotal * ratio` where `ratio = (subtotal − discountTotal) / subtotal`, which spreads the bill discount proportionally so `sum(lineNet)` equals the discounted subtotal. Inclusive VAT is `lineNet − lineNet/(1+rate/100)`; exclusive is `lineNet * rate/100`; rate 0 contributes nothing.

```
getVatAmount  = Σ line.vat                       (all lines, inclusive + exclusive)
getGrandTotal = afterDiscount + Σ (exclusive ? line.vat : 0)
```

The behavioural change: previously `getGrandTotal` returned `afterDiscount` with no VAT added, so VAT-exclusive lines never contributed to the payable. Now exclusive VAT is added on top while inclusive VAT stays embedded. This is the correct fix, but it changes what `getGrandTotal` returns for any cart containing exclusive-VAT products. The author verified against `PaymentScreen`/`Receipt`/`CartScreen` that VAT is shown as an informational "รวมแล้ว" line and confirmed `getGrandTotal` is the single payable source — so the one place that matters already consumes the new total correctly. Downstream code that sums `getVatAmount` into a payable on top of `getGrandTotal` would double-count; none was found in the touched set.

The `cartVat` suite covers the mix (inclusive-107 + exclusive-100 + 0%-50 → VAT 14, grand 264), the 10% bill-discount case (VAT 12.6, grand 237.6), inclusive-only (grand == subtotal), and empty cart. Not tested: multiple distinct non-zero rates in one cart (e.g. a hypothetical non-7% line) — the code handles it generally but no case pins it.

### PaymentScreen VAT label

The hardcoded `VAT 7% (รวมแล้ว)` is replaced by a `useMemo` that shows `VAT {rate}% (รวมแล้ว)` only when every taxed line is inclusive at a single rate, and falls back to the neutral `ภาษีมูลค่าเพิ่ม (VAT)` otherwise. This stops the UI asserting a flat inclusive 7% when lines differ. No new import.

### CSV import/export

`ImportExportScreen` is a real implementation: `parseCsv` strips the BOM, handles CRLF/LF and quoted/escaped fields; `resolveHeaderIndex` maps Thai headers flexibly so both the pricing-template columns and product-field columns parse. Per-row validation flags empty code/name, non-positive sale price, and unknown category (checked against active `MOCK_CATEGORIES`), rendering a real valid/error summary and preview with an errors-only filter. On confirm, existing codes route to `updateProduct` and new codes to `addProduct` with a full `ProductMaster` (including a base UOM); error rows are skipped. Export and template download both emit real CSV via `Blob` + `URL.createObjectURL` with a BOM so Excel reads Thai. Everything is `Platform.OS === 'web'` guarded with a Thai native fallback, and loading/importing/done/empty states are all present.

One ordering note on the category check: `validateRow` only rejects a category that is non-empty and unknown — a blank category passes validation and is stored as an empty `categoryId` with `categoryName` falling back to the raw cell. That's a lenient-but-reasonable choice for a mock import, not a defect.

### Image picker and audit

The product image button triggers a hidden `<input type=file accept=image/*>`, reads via `readAsDataURL`, stores the data URI in state, and renders a preview with เปลี่ยนรูป/ลบรูป actions; the URI is saved into `ProductMaster.image` (field exists in the type). Native shows the Thai web-only alert. The price-change audit replaces `console.log` with `logAction('สินค้า', 'เปลี่ยนราคา', ...)` gated on `isEdit && product.salePrice !== sale`.

The carried-over gap: `ProductNavigator.onSaved` only calls `goBack()` and does not persist to `productStore`, so on the mobile edit flow the new image and price never reach the store — the audit entry still fires. The author flagged this rather than expanding scope to rewire navigation, which is the right call. The web product screens and the CSV path write to `productStore` directly and are unaffected.
